01 / SOURCE WALKTHROUGH

One tap, one owned journey

The normal app composition joins SwiftUI intent, domain rules, two writing clients and one acceptance boundary.

The composer collects a person, relationship, occasion, register, tone, length and optional “true thing”. MomentModel.moment creates a normalized MomentInput, using the current device locale. startDraft() refuses an invalid or already-running request. startGeneration captures the request, cancels obsolete work and owns the single retained task.

A typical everyday Write starts on device. A sympathy, pet-loss or apology Moment normally starts online through the careful route. The concrete clients are composed in the app target; the view never chooses a provider. An absent gateway endpoint gives an explicit unconfigured client.

Only after the service returns, cancellation is checked and the generation ID still matches does the model replace the visible bundle. A successful replacement saves the old bundle as a rewrite snapshot. The UI presents one editable message, pressure feedback, Copy, native ShareLink and explicit Save. Generating a message does not itself save it to the library or send it to a recipient.

Why this exists

A single owner makes the result belong to the exact request that produced it. It prevents a late request from replacing newer wording and keeps transport details out of the product UI.

The guard ladder

These checks have different jobs: some prohibit generation, some route it, and some merely advise the writer.

Initial service routing repeats context validation; adjustment routing repeats safety but has no equivalent context guard.

Revocation boundaryPrivacy settings remove the stored version and show a notice. The callback does not cancel an in-flight generation. This is a gate for subsequent online operations, not recall of data already sent or a per-byte transport interlock.

Pressure acceptanceLocal findings merge with model-supplied findings. They advise rather than reject; Keep acknowledges the current text/lane/check hash. Clean up requests Direct and acknowledges the resulting bundle. A changed draft/check resets acknowledgement.

Two lanes, asymmetric fallback

Product lane labels are not provider tiers. “Careful” is not a Premium-only gate.

requiresCarefulLane is true for every assemble register. For confess or react, sympathy, pet sympathy and apology make it true. Register alignment switches react↔assemble as appropriate. The gateway has a broader sensitive-occasion set for prompt/quality rules: sympathy, get well, encouragement, apology and pet sympathy. Those server rules do not themselves select the app’s lane.

FailurePrivate → gatewayCareful initial → private
Permission required / contentBlockedNeverNever
Cancellation / cancelled transportNeverNever
Offline / usageLimitReachedNeverAllowed
Timeout / rateLimited / requestNeedsFreshKeyAllowed, with current grantAllowed
serviceUnavailable / unexpectedResponseAllowed, with current grantAllowed
Untyped errorAllowed, with current grantAllowed

There is at most one app-level fallback, not a recursive ping-pong. Failure of the second lane escapes to the model. An everyday private fallback is labelled standardDraft; a successful private fallback retains privateDraft. Named Warmer, Shorter and Direct adjustments follow the existing bundle lane. An online bundle’s adjustment never falls back private. Another/rewrite is a fresh initial draft, without old wording in the prompt.

Foundation Models maps guardrail/refusal to contentBlocked; assets/unavailability to serviceUnavailable; context overflow, unsupported guide/language and decoding failure to unexpectedResponse; concurrency/busy to rateLimited. The generic gateway adapter does not classify provider refusal fields as a semantic content block: HTTP or parse failure can try another configured model and ultimately become 502/serviceUnavailable. Client support for HTTP 422 exists, but this handler does not emit 422.

Why this exists

The asymmetry lets a hard Moment still use a local draft during an outage or exhausted online allowance, while ensuring permission and explicit content blocks remain final. Adjustments preserve the route of the wording being reshaped.

04 / SOURCE WALKTHROUGH

Inside the gateway

Authentication, a durable request ledger and output validation surround every configured provider attempt.

Auth first. POST is required (OPTIONS is handled). Normal mode validates the bearer with Supabase auth.getUser(). Development mode is an explicit alternative: when its anonymous flag is enabled it requires the separate secret and uses the common dev-anonymous subject, even if a bearer is supplied. Privileged database access stays in the Edge Function.

Validate before paid work. The parser accepts snake/camel wire aliases, validates taxonomy, spelling, lane and version 1 contracts, and checks a 1–120-character request key. An included header must exactly equal the body key. It replaces recognized instruction-injection patterns with length-preserving bullet markers, collapses whitespace and truncates by user-perceived Unicode grapheme clusters. Names cap at 80, locale at 40, include/avoid lists at 12×1,200 and context at 4,080; invalid list items drop out. Premium lane returns 403; local returns 503; only automatic/standard proceed. The native client requests standard.

Three generated, one presented. The gateway generates and quality-checks three candidates. The current iOS client selects only the first, without ranking, and discards the other candidates plus returned usage/retry metadata. The current app does not present a three-choice result.

Identity across retries. The app hashes intent+lane+contract versions and persists one pending initial-request UUID with that hash for reuse up to 24 hours. Success or fresh-key errors clear it; different/expired intent replaces it. Adjustments always get new UUIDs. The server computes its own fingerprint after sanitization, excluding app/build metadata, and scopes the key by authenticated subject.

Ledger decisionImplemented effect
Atomic reservationA subject advisory lock serializes quota decisions. Free authenticated policy is one lifetime completed request; entitled policy is 500/month. Active reservations count. Burst policy is 10 provider-bound attempts in 60 seconds. These repository values are not approved numerical customer promises or verified deployed settings.
Duplicate or occupied identityCompleted + live payload → replay 200. Same key/different fingerprint → conflict 409. Live reservation → in-flight 409. Expired replay → 409, no new charge. Quota → 402. Burst → 429 plus Retry-After.
Lease and completionA 120-second lease can be reclaimed with a new attempt token. Stale tokens cannot finalize the new attempt. Completed finalization atomically increments usage once and stores response; failed finalization does not charge. Matching repeated finalization is idempotent.
Cancellation and uncertaintyIncoming abort stops provider fallback; observed cancellation after reservation attempts failed finalization and returns 499. If finalization itself fails, no confirmed ledger outcome can be claimed. A success whose finalize fails is still returned as 200, with a diagnostic log marker. Cancellation arriving during successful finalize is not rechecked afterward.
Replay retentionReplay eligibility: 24h. Hourly cleanup physically clears expired payloads, then metadata becomes eligible seven days after updated_at; clearing the payload updates that timestamp. Rate rows become eligible after one hour. This is repository SQL, not proof the hosted job is running.

Prompt and provider loop. The prompt requests three emotionally distinct message bodies, supplied facts only, no greetings/sign-offs, no implementation references, context-as-data, occasion/relationship guidance, length and locale. Funny/playful/sarcastic becomes gentle for sensitive occasions. Religious references are guided by occasion/context. These are prompt instructions, not all enforced output predicates.

Actual adapter: only openai-compatible is executable. Missing mode/URL/key/model yields unconfigured. It POSTs system/user messages, model, temperature (default 0.7), max_tokens (900) and optional JSON mode to one configured URL. Each model attempt has its own default 15s provider timer (configurable 1–60s). There is no separate server-wide total timer or fixed fallback-count cap. Models run sequentially; errors and quality failures advance, incoming abort stops. The same prompt may reach more than one configured model.

Planned / experimental · OpenRouter: no dedicated OpenRouter mode, headers, routing policy or production binding was found. A historical strategy mention is not implementation evidence. A compatible endpoint could be configured, but that is not evidence OpenRouter is configured, deployed or privacy-qualified. The current response still reports fallback_status=none even after a provider-model fallback.
Why this exists

Retries, parallel last-slot requests and lost mobile responses must not independently spend money or consume allowance. The ledger makes permission to call a provider an atomic server decision; token ownership protects it against late attempts.

Failure is a journey too

A failed request, changed intent and uncertain deletion must not be treated as the same event.

OfflinePrivate work does not need network. A direct careful offline error can fall back private; if that succeeds the user sees a private draft. If no eligible route succeeds, an offline/unavailable state appears and existing wording remains. Offline from private is explicitly not routed online.
Timeout / busy / provider failureEligible initial fallback runs within the same total service attempt. Exhausted route gives a typed notice/retry. Online adjustments stop at their error. A retry is user-driven; Retry-After and retry_eligibility are not an automatic client retry scheduler.

The network boundary is explicit

Private prompt context stays in the private client. Online writing crosses two hops after one app-level permission gate.

Private prompt: person, relationship, occasion, register description, tone, length, locale, true detail, approved matching facts and approved style card; adjustment adds the current message and action. The private client uses a fresh Foundation Models session and structured output. No provider network call is made by that client.

Careful app → gateway payload: person name, taxonomy (relationship/occasion/tone/length), locale and automatic spelling preference, detail in things_to_include, register description in user_context; adjustment adds its instruction and current draft. It also carries request key, versions, app/build/platform and bearer or guarded development credential. The current Moment client supplies no installation ID and sends no vault record objects.

Two easy-to-miss boundaries. Each include or exclusion item keeps the native 1,200-character Moment-detail bound through server parsing, measured as user-perceived Unicode grapheme clusters. Adjustment userContext keeps a 4,080-character wire bound: 4,000 for the accepted draft and 80 for its fixed register-and-label wrapper. Vault records are not directly sent, but a private draft can incorporate their facts; an eligible private adjustment fallback then sends that draft text online after permission. “No vault objects” does not mean “no memory-derived wording can ever leave”.

Gateway → provider: the writing fields become a system/user prompt. Request key and bearer are transport/ledger material, not prompt fields. The provider API key stays server-side. The same writing prompt may be sent sequentially to primary and fallback models. Source does not establish production endpoint configuration or provider retention, training or data-use terms; this walkthrough makes no such claim.

Other network surfaces are distinct: Apple/Supabase login and refresh, Apple credential checks, App Store purchases/restore, Apple token exchange/revocation, account deletion and server App Store event/reconciliation functions. Online-writing consent does not govern those account/payment requests. Copy, Share and export are explicit user transfers; the writing service never sends the message to its recipient.

Storage is part of privacy. Gateway replay stores generated text for a 24h eligibility window, with physical removal on scheduled cleanup. Local recovery and handoffs use UserDefaults; only the vault has explicit directory backup exclusion here. Diagnostics intend metadata only, not raw writing, prompts, tokens or provider bodies. Production-host logging retention is not established by these source paths.

Why this exists

Consent belongs immediately before the route that can transfer writing, including fallback. Separating that transfer from sign-in, purchase and explicit sharing makes the privacy promise inspectable rather than implied by a UI label.

Identity, purchases and deletion

Three independent forms of ownership: ProsePal account, on-device writing and App Store subscription.

Sign in. The model generates a cryptographic nonce; Apple receives its SHA-256. Supabase receives the ID token and raw nonce. The authenticated exchange-apple-token boundary binds the authorization-code response to the caller’s Apple identity and configured client ID, retaining refresh material for later revocation. Only after that succeeds does the app persist its Supabase session and Apple credential user ID. No contact scopes are requested. Failed intermediate exchange is not proof no remote account/session was created.

Session continuity. AuthSessionController serializes/coalesces refresh, persists rotated credentials before returning them, and drains refresh before replacement/clear. Offline/server failure preserves a refreshable session; terminal refresh rejection clears it. Apple revoked/not-found/transferred checks clear account state, with fail-closed revocation notifications and a more tolerant ordinary-launch transient error path. These actions do not erase the local vault.

Purchases. StoreKit loads configured products, verifies relevant transactions and renewal status, and distinguishes active (including grace period), confirmed inactive and unknown. Unknown never creates Premium; same-account last-known verified access may remain during transient failure. Account identity change or confirmed inactivity clears access. A valid signed-in UUID is used as appAccountToken; explicitly mismatched ownership fails closed, while unlinked purchases support buying before sign-in. Transaction updates and purchases are finished only after compatible, correlated entitlement convergence; failed convergence leaves delivery unfinished for redelivery. Pending, cancellation or unverified purchase never unlocks access.

Server entitlement is separate. Verified App Store notification/reconciliation handlers update server capability. Setting the UI Premium flag cannot grant gateway quota. The repository is not evidence that production StoreKit products, account linkage, notifications or reconciliation have passed live acceptance.

App Store subscription cancellation remains a separate Apple management action.
Why this exists

Purchase truth must not depend on a transient network failure or the wrong signed-in account. Deletion must distinguish “confirmed gone” from “the response disappeared” before erasing the user’s only local copy.

Read the implementation literally

The broad canonical architecture matches the major ownership boundaries. These source-level qualifications change how it should be explained.

FindingEvidence / implication
Received HTTP 499 versus client cancellationNormal URLSession cancellation stays cancellation. GatewayMessageWritingClient has no explicit 499 case: a received HTTP 499 maps through unexpectedResponse and can become fallback-eligible where routing permits. This received-499 path is narrower than normal client cancellation; the canonical generation contract distinguishes them.
Provider refusal classificationFoundation Models refusal maps to contentBlocked, but the generic online adapter has no semantic refusal extraction; provider failure may run fallback models and become serviceUnavailable. The canonical AI generation documentation records this distinction.
First candidate is not rankedGateway promises three distinct options with equal contract status. GatewayCarefulMomentClient selects first and drops the other options plus usage/retry metadata. No quality ranking chooses it.
Recovery scope is narrower than “working state”Recovery is conditional on an existing bundle. New composer input before the first result is not persisted. Input mutation clears existing recovery. A malformed decoded envelope is ignored; there is no expiry.
Permission is prospectivePrivacy control says future drafts ask first, matching its code. Revocation is not wired to stop active generation; the store is not rechecked at result acceptance.
Deadlines / charging have limitsStructured child cancellation is cooperative. Observed pre-final cancellation attempts no-charge failure, but a cancel during completed finalization is not rechecked, and success is returned even if finalization fails. Avoid describing all client cancellation as a guaranteed server refund.
Historical wording is not product architecturegenerate-card file header still calls itself the first non-production slice for the native rewrite; AGENTS and canonical architecture say the SwiftUI app is the only current implementation. No OpenRouter implementation is established by the historical strategy mention.

These findings are static source observations and consequences of call order, not newly executed app regression tests or a production audit. No backlog aspiration is used as implementation evidence; planned behaviour is separate from these implemented paths.

Why this exists

A product owner needs both the strong design and its exact limits. This page explains current behaviour without silently promoting intended behaviour into a guarantee.

11 / SOURCE WALKTHROUGH

Why this is impressive

What feels like one tap is a coordinated set of privacy, reliability and editorial decisions.

Privacy survives fallback

A local technical failure cannot quietly authorize online writing. The same current-policy gate covers initial careful work and online adjustments.

A result belongs to a Moment

Task ownership and generation identity protect the recipient and wording from obsolete completions. Technical failure preserves the draft already in hand.

Mobile uncertainty is designed for

Durable request identity, atomic reservation, replay and attempt tokens address double charging, competing last-slot requests and stale finalization.

The writer stays in control

Pressure feedback, editable text, recovery snapshots and explicit Save/Copy/Share make generation a starting point for human judgement.

Account state is honest

Unknown StoreKit state cannot invent access, and uncertain remote deletion cannot automatically destroy the only local copy.

Complexity has owners

The view asks for writing. Protocol boundaries isolate private runtime, gateway, auth, purchase and persistence details so their failure cases can be tested independently.

The impressive part is the coordination: safeguards are placed at the state transition where they matter. The source qualifications above remain essential—these mechanisms reduce specific classes of bugs; they do not establish perfect output quality, hard cancellation or provider privacy terms.

Why this exists

One simple product interaction deserves infrastructure that handles ordinary mobile failure without making the writer understand that infrastructure.
